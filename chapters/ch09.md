## 9.1 멀티 에이전트 아키텍처 개념: 오케스트레이터와 서브에이전트

Claude Code의 가장 강력한 기능 중 하나는 여러 AI 인스턴스를 동시에 운영하는 것입니다. 혼자 모든 걸 하던 방식에서, 전문화된 팀이 협력하는 방식으로 전환합니다.

### 오케스트레이터 패턴

```
멀티 에이전트 아키텍처:

┌─────────────────────────────────────────────────┐
│              오케스트레이터 (메인 Claude)          │
│         "전체 기능 개발을 조율합니다"              │
└──────────────┬──────────────┬───────────────────┘
               │              │              │
               ▼              ▼              ▼
    ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
    │ 서브에이전트1  │ │ 서브에이전트2  │ │ 서브에이전트3  │
    │  (백엔드 API) │ │ (프론트엔드)  │ │  (테스트)    │
    └──────────────┘ └──────────────┘ └──────────────┘
         ↓                  ↓                ↓
    [독립 작업]         [독립 작업]        [독립 작업]
         └──────────────────┴────────────────┘
                            ↓
                    [결과 통합 & 검증]
```

### 언제 멀티 에이전트가 효과적인가?

```
멀티 에이전트가 효과적인 상황:
✅ 독립적으로 분리 가능한 작업
✅ 병렬 실행으로 시간 절약 가능
✅ 각 영역에 전문화된 컨텍스트 필요
✅ 컨텍스트 윈도우가 너무 커지는 대규모 작업

단일 에이전트가 더 나은 상황:
⚡ 작업 간 의존성이 높음
⚡ 빠른 피드백 루프가 필요
⚡ 규모가 작은 작업
```

## 9.2 git worktree를 활용한 병렬 작업 설정

git worktree는 하나의 git 저장소에서 여러 브랜치를 동시에 체크아웃할 수 있게 합니다. 각 Claude 인스턴스가 충돌 없이 독립적으로 작업할 수 있는 환경을 제공합니다.

### git worktree 기본

```bash
# 현재 저장소 상태 확인
git worktree list

# 새 worktree 생성
git worktree add ../project-feature-auth feature/auth-module
git worktree add ../project-feature-ui feature/ui-redesign

# 결과: 두 개의 독립적인 작업 디렉토리
# ../project-feature-auth  → feature/auth-module 브랜치
# ../project-feature-ui    → feature/ui-redesign 브랜치

# worktree 삭제
git worktree remove ../project-feature-auth
```

### 멀티 에이전트 환경 구성 스크립트

```bash
#!/bin/bash
# setup-parallel-agents.sh

PROJECT_ROOT=$(pwd)
PROJECT_NAME=$(basename $PROJECT_ROOT)

echo "멀티 에이전트 환경 설정 중..."

# 백엔드 작업용 worktree
git worktree add "../${PROJECT_NAME}-backend" -b feature/backend-api
echo "✓ 백엔드 worktree 생성: ../${PROJECT_NAME}-backend"

# 프론트엔드 작업용 worktree
git worktree add "../${PROJECT_NAME}-frontend" -b feature/frontend-ui
echo "✓ 프론트엔드 worktree 생성: ../${PROJECT_NAME}-frontend"

# 테스트 작업용 worktree
git worktree add "../${PROJECT_NAME}-tests" -b feature/test-coverage
echo "✓ 테스트 worktree 생성: ../${PROJECT_NAME}-tests"

echo ""
echo "각 터미널에서 다음을 실행하세요:"
echo "  터미널 1 (백엔드):    cd ../${PROJECT_NAME}-backend && claude"
echo "  터미널 2 (프론트엔드): cd ../${PROJECT_NAME}-frontend && claude"
echo "  터미널 3 (테스트):    cd ../${PROJECT_NAME}-tests && claude"
```

## 9.3 실전 예제: 프론트엔드/백엔드 동시 개발

실제 사용자 관리 기능을 프론트엔드와 백엔드에서 동시에 개발하는 시나리오입니다.

### 작업 분배

```
메인 Claude (오케스트레이터):
─────────────────────────────
"사용자 프로필 편집 기능을 개발합니다.
 - 백엔드: PUT /api/users/:id 엔드포인트
 - 프론트엔드: ProfileEditForm 컴포넌트
 두 작업을 병렬로 진행합니다."
```

**터미널 1 - 백엔드 에이전트:**
```bash
cd ../project-backend
claude
```

```
> 사용자 프로필 수정 API를 구현해줘.

  엔드포인트: PUT /api/users/:id
  입력: { name, bio, avatarUrl }
  검증:
  - name: 2-50자
  - bio: 최대 200자 (선택)
  - avatarUrl: 유효한 URL 형식

  기존 UserController, UserService, UserRepository 패턴 따라줘.
  Zod로 입력 검증하고, 단위 테스트도 작성해줘.
```

**터미널 2 - 프론트엔드 에이전트:**
```bash
cd ../project-frontend
claude
```

```
> 사용자 프로필 편집 폼 컴포넌트를 만들어줘.

  컴포넌트명: ProfileEditForm
  기능:
  - 이름, 자기소개, 아바타 URL 입력
  - react-hook-form으로 폼 관리
  - zod 스키마로 클라이언트 검증
  - 제출 시 PUT /api/users/:id 호출
  - 성공/실패 토스트 메시지

  Tailwind CSS 사용, 기존 컴포넌트 스타일 참고해서 만들어줘.
```

두 에이전트가 동시에 작업하는 동안, 메인 오케스트레이터는:

```
> 백엔드 API 스펙을 OpenAPI 문서로 작성해줘.
  그리고 프론트엔드가 사용할 TypeScript 타입도 shared/types에 만들어줘.
```

### 작업 완료 후 통합

```bash
# 각 브랜치 완료 후 메인에서 통합
cd ../project-main
claude
```

```
> 다음 브랜치들을 main에 통합해야 해:
  - feature/backend-api
  - feature/frontend-ui

  통합 전에 충돌이 있는지 확인하고,
  통합 테스트를 실행해서 두 부분이 잘 연동되는지 확인해줘.
```

## 9.4 에이전트 간 충돌 방지와 작업 결과 통합 전략

### 충돌 방지 원칙

```
파일 소유권 원칙:
┌────────────────────────────────────────────────┐
│ 각 에이전트는 자신만의 파일 영역을 가집니다    │
│                                                │
│ 백엔드 에이전트: src/api/**, src/services/**   │
│ 프론트엔드 에이전트: src/components/**, pages/** │
│ 공유 타입: 메인 오케스트레이터만 수정          │
└────────────────────────────────────────────────┘
```

### 인터페이스 계약 먼저 정의

```bash
# 작업 시작 전, 메인 오케스트레이터가 계약 정의
> 백엔드와 프론트엔드가 공유할 API 계약을 먼저 정의해줘:
  1. shared/types/api.ts - API 요청/응답 타입
  2. shared/contracts/user-api.ts - API 엔드포인트 상수

  이 파일들이 정의된 후 각 팀이 독립적으로 작업할 수 있어.
```

```typescript
// shared/types/api.ts (먼저 정의)
export interface UpdateUserRequest {
  name: string;
  bio?: string;
  avatarUrl?: string;
}

export interface UpdateUserResponse {
  id: string;
  name: string;
  bio: string | null;
  avatarUrl: string | null;
  updatedAt: string;
}
```

### 통합 체크리스트

```bash
# 통합 전 자동 검증
> 두 브랜치를 합치기 전에 다음을 확인해줘:
  1. 백엔드 API가 shared/types와 일치하는지
  2. 프론트엔드가 정확한 API 엔드포인트를 호출하는지
  3. 에러 케이스 처리가 양쪽에서 일관성 있는지
  4. TypeScript 컴파일 에러 없는지
```

> **💡 팁:** 멀티 에이전트 작업에서 가장 중요한 것은 **작업 분리 명확성**입니다. 두 에이전트가 같은 파일을 수정하면 충돌이 발생합니다. 작업 시작 전에 파일 소유권을 명확히 정의하세요.

---

## 핵심 요약

1. **오케스트레이터-서브에이전트** 패턴으로 복잡한 작업을 병렬 처리합니다
2. **git worktree**로 각 에이전트가 독립적인 브랜치에서 작업합니다
3. 공유 타입/인터페이스를 **먼저 정의**하면 충돌이 줄어듭니다
4. **파일 소유권**을 명확히 하여 에이전트 간 충돌을 방지합니다
5. 통합 전 자동 검증으로 품질을 보장합니다

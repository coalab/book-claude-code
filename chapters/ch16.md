## 16.1 효과적인 작업 지시 패턴: 명확성, 범위, 출력 형식

### 황금 프롬프트 공식

```
효과적인 프롬프트 = 역할 + 목표 + 제약 + 출력 형식

역할: "당신은 시니어 백엔드 엔지니어입니다"
목표: "결제 모듈의 에러 처리를 개선해야 합니다"
제약: "기존 API 인터페이스는 유지해야 합니다"
출력 형식: "변경된 파일 목록과 각 변경 이유를 설명해주세요"
```

### 명확성 원칙

```bash
# ❌ 모호한 지시
"코드 개선해줘"

# ✅ 명확한 지시
"src/services/payment.ts 파일의 에러 처리를 개선해줘.
 구체적으로:
 - 네트워크 에러는 3회 재시도 (exponential backoff)
 - 비즈니스 에러 (잔액 부족, 카드 만료)는 즉시 실패
 - 모든 에러는 error.log에 기록
 - 에러 응답 형식: { code: string, message: string, retry: boolean }"
```

### 범위 지정

```bash
# 범위를 명확히 제한
"UserService의 createUser 메서드만 수정해줘.
 다른 메서드나 파일은 건드리지 마."

# 단계적 작업 요청
"먼저 계획만 세워줘. 실제 코드 수정은 내가 OK 하면 진행해."
```

### 출력 형식 지정

```bash
# 마크다운 구조 요청
"다음 형식으로 분석 결과를 작성해줘:
 ## 발견한 문제점
 - [문제1]: 설명 (파일:줄번호)
 - [문제2]: 설명 (파일:줄번호)

 ## 권장 해결 방법
 [각 문제별 해결책]

 ## 우선순위
 1. 즉시 수정 필요
 2. 다음 스프린트
 3. 기술 부채"
```

### 예제 기반 요청

```bash
"기존 UserRepository의 스타일을 참고해서
 ProductRepository를 만들어줘.

 기존 패턴:
 - PrismaClient를 의존성 주입
 - 모든 메서드는 async/await
 - 에러는 throw하지 않고 Result<T, E> 타입으로 반환
 - 페이지네이션은 cursor-based 방식

 동일한 패턴으로 Product CRUD를 구현해줘."
```

## 16.2 Think 모드 활용: 복잡한 문제에서 추론 유도하기

### Think 모드란?

Claude Code에 복잡한 문제를 줄 때 "think", "think hard", "ultrathink" 같은 키워드를 포함하면 더 깊은 추론을 유도할 수 있습니다.

```bash
# 일반 요청
"이 알고리즘을 최적화해줘"
→ 빠른 응답, 표면적인 최적화

# Think 모드
"이 알고리즘의 시간/공간 복잡도를 분석하고
 최적화 방법을 think through해줘"
→ 더 깊은 분석, 트레이드오프 고려

# 더 강한 추론
"아키텍처를 변경하기 전에 think hard about:
 - 현재 시스템의 병목
 - 각 대안의 장단점
 - 마이그레이션 리스크"
```

### Think 모드 활용 사례

**복잡한 버그 분석:**
```bash
"이 버그가 왜 발생하는지 단계별로 think through해줘.
 모든 가능한 원인을 나열하고,
 각 원인의 가능성을 평가한 후,
 가장 유력한 원인부터 검증해줘."
```

**아키텍처 결정:**
```bash
"현재 모놀리식 구조를 마이크로서비스로 전환할지 고민해줘.
 Think hard about:
 1. 현재 시스템 규모와 팀 크기
 2. 전환 비용 대비 이점
 3. 단계적 전환 vs 빅뱅 전환
 최종 권장사항과 근거를 제시해줘."
```

## 16.3 컨텍스트 압축과 /compact 명령 전략

### 컨텍스트 관리의 중요성

```
컨텍스트가 너무 길면:
- 응답 품질 저하
- 비용 증가
- 응답 속도 저하
- 최근 내용에 집중하지 못함

적절한 컨텍스트 관리가 성능에 직결됩니다.
```

### /compact 활용 전략

```bash
# 언제 /compact를 사용할까?
- 대화가 20-30 턴을 넘어갈 때
- 새로운 주제나 파일로 전환할 때
- "맥락을 잃은 것 같다"는 느낌이 들 때
- 비용이 급격히 증가할 때

# 사용법
/compact

# compact 후 재확인
"방금 compact 했어. 우리가 작업 중이던 내용을 요약해줘.
 다음 단계가 뭔지도 알려줘."
```

### 선택적 컨텍스트 전략

```bash
# 불필요한 파일 제외
"auth 모듈 작업할 거야.
 관련 없는 파일들(payment, analytics 등)은
 컨텍스트에 올리지 마."

# 요약본 활용
"이 1000줄 짜리 파일 전체 대신,
 public 함수들의 시그니처와 주석만 읽어줘."

# 세션 분리
# 큰 작업은 여러 세션으로 나눔
세션1: API 설계
세션2: 백엔드 구현
세션3: 프론트엔드 구현
세션4: 테스트 작성
```

## 16.4 모델 선택 전략: claude-opus vs claude-sonnet 상황별 선택

### 모델 특성 비교

| 특성 | Claude Opus | Claude Sonnet |
|------|------------|---------------|
| 성능 | 최고 | 높음 |
| 속도 | 느림 | 빠름 |
| 비용 | 높음 | 보통 |
| 추론 능력 | 최고 | 우수 |

### 상황별 모델 선택

**Claude Opus 사용 시:**
```bash
# 복잡한 아키텍처 설계
"전체 마이크로서비스 아키텍처를 설계해줘"

# 복잡한 알고리즘
"이 NP-완전 문제의 근사 알고리즘을 설계해줘"

# 레거시 코드 심층 분석
"이 복잡한 레거시 시스템의 동작을 완전히 이해해줘"

# 중요한 보안 리뷰
"이 인증 시스템의 보안을 철저히 검토해줘"
```

**Claude Sonnet 사용 시:**
```bash
# 일반 코딩 작업
"CRUD API 엔드포인트 추가해줘"

# 리팩토링
"이 함수를 더 읽기 쉽게 리팩토링해줘"

# 문서 작성
"이 클래스의 JSDoc을 작성해줘"

# 보일러플레이트
"React 컴포넌트 템플릿을 만들어줘"
```

### 모델 변경 방법

```bash
# 세션 중 모델 변경
/model claude-opus-4-5

# 특정 작업만 Opus로
"이 복잡한 설계 결정은 /model claude-opus-4-5로 분석해줘"

# .claude/settings.json에서 기본 모델 설정
{
  "model": "claude-sonnet-4-6"
}
```

> **💡 팁:** 대부분의 일상적인 개발 작업은 Sonnet으로 충분합니다. 복잡한 설계 결정이나 어려운 버그 분석 시에만 Opus로 전환하는 전략이 비용 효율적입니다.

## 핵심 요약

1. **황금 프롬프트 공식** (역할+목표+제약+출력형식)으로 더 나은 결과를 얻습니다

4. 복잡한 작업엔 Opus, 일반 작업엔 Sonnet으로 **비용을 최적화**합니다
5. 예제 기반 요청으로 기존 코드 스타일을 자연스럽게 유지합니다
